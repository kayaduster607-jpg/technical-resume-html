# 逐个贡献点写成：问题＋解决＋提升效率

开始深挖具体贡献点、把访谈答案整理成条目或审核成稿时读取。适用于不同岗位；按职业背景选择方法与证据，不要求每段经历包含技术实现。

## 视频的具体例子

依据用户提供视频画面字幕与分段标签整理；技术术语作可读化归一，不是逐字音频转录。

| 位置 | 画面中的信息 | 写作作用 |
| --- | --- | --- |
| 约 01:01 | 黄色字幕明确写“问题＋解决＋提升效率” | 每个具体点采用三段结构 |
| 约 01:09—01:11 | 用户并发提交的编号冲突问题 | 先点明问题及触发场景 |
| 约 01:13—01:17 | 切面拦截请求、Redis、尝试写保证幂等性 | 具体解决机制的第一层 |
| 约 01:19—01:23 | 数据库查表后，通过加行级悲观锁实现双重保障 | 具体解决机制的第二层 |
| 约 01:25—01:31 | 跨表文号序号一致，避免前端重复、数据重复与提交失败 | 提升效率／最终效果；视频此处没有量化提升率 |
| 约 01:35—01:37 | “问题 解决方法 效果”及“业务 实现方法 效果” | 建设型功能同样需要交代效果 |

这个例子展示的是：不是“用了 Redis 和数据库锁”，而是说明**什么问题值得处理 → 两种机制如何处理 → 最后改善什么**。不要把视频作者的技术结论自动认可为适用于所有并发系统；真实效果依赖幂等键、写入条件、事务与锁范围等实际实现。

## 逐点深挖，不只问整个项目

对每个待保留的点，维护一张小卡：

```text
贡献点：
问题：什么场景、什么触发、原来有什么损失？
解决：本人做了什么、采用什么方法或机制、为什么这样选择？
提升效率／最终效果：改前改后有什么差别、谁受益、怎样验证？
来源与状态：用户回答／工作记录／作品／代码／报告；已完成／验收／试点／推广／计划。
```

技术岗位示例：如果用户只说“加了缓存”，不要直接写“提升查询效率”。接着问：

1. 为什么需要缓存，原来哪些请求慢或重复读取？
2. 缓存什么、何时失效、如何处理过期和并发，哪些是你写的？
3. 加入后减少了什么查询或计算，有没有前后耗时或调用次数？
4. 测试环境、样本范围与正确性验证是什么？

如果用户只说“保证幂等”，继续问重复操作会造成什么后果、幂等标识如何产生、并发写入如何判定、失败重试怎么处理，以及怎样证明没有重复记录。不要根据一个技术名替用户补完方案。

如果用户给了问题和方案，但没有提升效果，继续追问第三段：**原来需要什么，改完省了什么、避免了什么、稳定了什么？** 不因前两段已经能写成顺畅句子而结束访谈。

## 非技术岗位的追问

- **运营与市场：**活动服务谁、原来卡在哪、你如何选择渠道和内容、哪些行动由你完成、统计周期和效果归因是什么？不要把流量或转化的变化自动全部归给一个人。
- **销售与客户服务：**客户处于什么阶段、遇到什么异议或服务问题、你采用什么跟进或处理方法、后续发生什么变化、个人与团队业绩如何区分？
- **设计与产品：**需求与研究发现是什么、为什么选该方案、怎样迭代和验证、用户或业务反馈有什么变化？不能仅根据“做了原型”推导转化提升。
- **职能与项目协作：**原流程的重复、遗漏或等待在哪里、你推动了什么标准或交接方式、谁采纳、改后少了什么步骤或错误、有哪些记录？
- **管理与咨询：**你拥有多大决策与资源权限、团队和合作方分别做什么、采取了什么组织或业务措施、交付与成果如何验收？团队产出不能直接写成个人独立完成。

转岗或重返职场时，追问经历中可迁移到目标岗位的方法与证据，而不是把旧职位改成新职位。输出语言变化时保留同一事实边界、职位级别与指标口径。

## 弱句到完整句

以下均为结构教学的假设案例，不代表用户已有经历；只有相应事实经确认后才能用于简历。

| 弱句 | 按三段式重写的方向 |
| --- | --- |
| 使用 Redis 做接口防重 | 针对重复点击造成重复建单的问题，通过请求幂等键与条件写入拦截重复请求，使同一业务操作只产生一份订单记录；结果需有测试依据 |
| 优化了文档搜索 | 针对每次搜索重复读取片段的问题，将逐条读取改为批量查询并复用带失效机制的缓存，减少数据库往返并缩短搜索耗时；有测量后补前后值与范围 |
| 增加 Wiki 版本号 | 针对多人编辑时旧内容覆盖新修订的问题，通过提交时校验预期版本并拒绝过期写入，保留较新的修订并向冲突编辑返回明确提示；需核实实际行为 |
| 修复 SSE 连接问题 | 针对流式响应期间数据库连接长期占用的问题，调整连接获取和释放时机，使连接在数据库操作后及时归还，降低长会话占池影响；需核实生命周期与验证结果 |
| 负责跨部门交接 | 针对交接材料不完整、需要反复确认的问题，梳理清单、责任人与验收节点，使接收方按统一标准核对内容，减少遗漏带来的往返沟通；需确认实际采用与改善 |
| 做过用户运营 | 针对不同用户收到相同信息、跟进优先级不明确的问题，按需求分组并建立跟进记录，使团队能够选择对应内容与处理顺序；不未经验证声称留存或转化提升 |
| 负责客户跟进 | 针对客户问题在多人之间重复传递的情况，集中记录需求、责任人与下一步动作，使相关人员能接续处理并查到未完成事项；业绩归因与后续效果需核实 |
| 带领团队完成项目 | 针对任务依赖与责任边界不清的问题，明确分工、里程碑与异常升级路径，使团队能够识别阻塞并协调资源；需核实本人权限、团队贡献及交付结果 |

定量表达示范仅用字段：

> 针对【触发场景与问题】，通过【具体机制】，将【同一口径的原值】降至【新值】，在【环境、样本、测量方式】下验证【效率变化及正确性】。

没有数字时，第三段可以是验证过的“拦截过期写入、避免重复记录、缩短人工步骤、支持自动恢复、消除特定故障”。不要只写“显著提升效率”“增强稳定性”“效果良好”。

没有前后对照、没有故障复现或验证、也无法确认定性改善时，明确效果尚不清楚，继续询问或建议补做验证；不要把机制的理论作用写成用户已经取得的收益。用户要求先出草稿时，可用“实现【已确认功能】”描述已知范围，在正文外标明效果待核实。

## 写入 v28 HTML 时

“主要贡献”或“主要职责”的一个 `li` 就是一条完整的“问题＋解决＋提升效率”。短标题概括该点的岗位价值，后面一句或两句讲清三段。不要把第三段全部剥离到经历末尾，否则阅读单个贡献点时仍然只看到任务清单。

项目末尾的“项目成果”用于汇总整体交付、综合评测或成本变化，避免逐字重复每个条目的效果。版面不够时先删重复说明，不删掉逐点的第三段。
